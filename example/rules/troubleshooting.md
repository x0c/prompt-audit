# 排查方法论

## 默认在本地排查

- 收到线上 URL、任务是复现或改代码时：默认只提取参数，请求打本地对应服务。
- 用户明确说查测试/线上并给了环境或凭据，或任务本身是查线上（如 公司内部追踪系统 / 公司内部 K8s 管控台），直接走对应环境。
- 「本地服务不通」：先确认服务已启动（看日志），再端口探测。

## 查到底，少回头确认

- 进程、容器、端口、日志、配置等只读信息自行查到底；仅决策/凭据/不可逆或对外动作才问。
- 明显可逆止血（停孤儿容器、改本地配置）直接做并报告；改路由/网关/远端等影响面大的先说明再做。

## 反复尝试无效必须先搜索

任何问题（不限于编译：报错、运行异常、接口不通、依赖冲突、环境问题、工具故障等）出现以下任一情况，立即停止盲目尝试，先用 `指定的搜索工具` 检索再继续：

- 同一问题已尝试 2 种以上方案仍无进展，或同一报错反复出现；
- 自行分析 2 分钟仍无结论。

同题不尝试超 3 种方案而不搜索；被无关脏状态阻塞时明确告知用户，不死磕。

## 数据修复必须全量扫描

批量数据问题先全量扫出全部坏记录，一次性修完并验证。

## 排查结论呈现格式

1. 一句话结论先行（成没成、修没修）。
2. 按实体分条，用中文业务名。
3. 每条三要素：现象 → 原因 → 解决动作。
4. ID 只作括号补充或省略。
5. 不只给 ID、不贴大段日志、不先说「执行正常」再说「但没生效」。

## 冒烟测试约定

- 每步独立输出：每个 Step 单独报告请求+响应+验证，不合并笼统汇报。
- 超时必须重试：网络/DNS 冷启动超时直接重试，不是跳过理由。
- 配置缺失找替代：找有完整配置的路径继续测，不直接跳过。

## 运行时调试（Java）

debug 运行中服务、追调用、看中间变量用 运行时诊断工具 MCP，不改代码加日志再重启：入参/出参 `watch`，分支 `trace`，Spring Bean 用 `ognl`。
